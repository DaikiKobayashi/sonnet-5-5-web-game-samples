# Dynamite Mole — 実装比較の結果

> 数値は実測したものだけを書いている。測っていないものは「未計測」と書く。
> 評価は、実装担当の自己申告ではなく、評価者(オーケストレーター)がブラウザで測った結果。測定コードと生データは [`eval/`](eval/) にある。

## 評価の方針

「全く同じである必要はなく、遊べる(起動でき、動かせて、クリアまでできる)形であればよい。仕様書にどれくらい従っているかも見たい」という方針で、次の 2 つを分けて見た。

1. **遊べるか**: 起動する・動かせる・爆弾で敵を倒せる・ステージをクリアして先へ進める・ゲームオーバーからやり直せる。
2. **仕様書への従い方**: 受け入れ基準 Must 40 件 / Should 15 件の達成度と、番号のついた基準に入らない相違点。

## 所見

### 実装の違い

- **動作・完成度**: Must は全員 40/40 で、動作の正しさ(数値・状態遷移・ステージ生成・保存・入力)では差が出なかった。差が出たのは、Should の S11(`low` のみ ×)、音量の規定、細かい相違(死亡中の入力の持ち越し、見た目の不具合)。
- **ゲームとしての手触り・面白さ**: 移動速度・導火線・炎の寿命・敵の速度・ステージ表などは仕様で数値が固定されているため、実測でも 5 実装でほぼ同じ(移動 4.48〜4.51 タイル/秒 など)。手触りの差は、数値ではなく、演出・アニメ・音・見た目に出る。面白さは評価していない(未計測)。
- **アセット(画づくり・アニメーション・音)の違い**: すべてコードから生成(PNG は favicon のみ、または全くなし)。差が大きかった項目。
  - `low`: 2px ドットの素朴な絵。敵の待機アニメは 2 フレーム。ゴーレムはほぼ静止。プレイヤーの待機の呼吸なし。
  - `medium`: 2px ドットで、太く読みやすい絵。敵は 3〜6 状態、待機の呼吸あり。環境光は弱い。
  - `high`: 1px ドットの細かい絵。壁の松明・光の漏れ・蛍・専用の喜びポーズ。
  - `xhigh`: 1px ドット。ビネット・壁の松明・ランタンの鎖・火の粉。ゴーストの追跡時の表情変化。
  - `max`: 1px ドット。火の粉・ゆらぐ松明・敵ごとに色分けされた死亡エフェクト・喜びポーズと紙吹雪・タイトルの視差と蛍。
  - 音: 5 実装とも Web Audio で合成し、title + ステージ 1〜5 がすべて別の曲、残り 30 秒以下でテンポが上がる。音量は `xhigh` `max` が仕様の範囲内、`high` がほぼ範囲内、`low` `medium` は BGM・ジングルとも超過(`low` の stage4 は 0.83 でクリップに近い)。
  - 見比べる画像: [`eval/screens/`](eval/screens/) の `sheet-a.png`(タイトル・導入・ステージ 1〜5・エンティティ)、`sheet-b.png`(出口・結果画面・一時停止)、`stage-bomb-flame.png`(5 ステージの床の上の爆弾と炎)、`enemy-idle-strips.png`(敵の待機アニメ)。
- **コード品質(構造・読みやすさ・テスト)**: 量は次のとおり(dist の JS / HTML の行数、バイト数)。行数だけでは品質は測れず、可読性は未評価。

- **仕様の解釈の違い**: 仕様が両方の読み方を許した点で分かれた。ライフ表示の `X3` / `x3`、ステージクリアのボーナス加算のタイミング(クリア画面に入る時点か、次へ遷移する時点か。`low` `xhigh` は入る時点、`medium` は遷移時と README に記載)、死亡演出中の入力の扱い(`low` `medium` は持ち越す)。

### effort による差

- **差が出た点**
  - Should の満点率: low 14/15、medium 以上は 15/15。アニメの枚数(S11)が分かれ目。
  - 音量の規定の遵守: high 以上が範囲内(high はほぼ)、low / medium は超過。
  - 演出・アセットの密度: effort が上がるほど、光・粒子・アニメ・装飾が増える。xhigh と max の差は、Should の達成度ではなく、密度と作り込み(max の敵ごとの死亡エフェクトなど)に出た。
  - 自己検証の量: `xhigh` は 3 ファイル、`max` は 21 ファイルの検証ツールを自分で書いて確かめていた。
- **差が出なかった点**: Must の合否(全員 40/40)、数値の正確さ(移動・導火線・炎・速度・タイマー)、仕様 3.3 のステージ生成(全員、参照実装と完全一致)、コンソールエラー(全員 0 件)。受け入れ基準の多くは、low でも満たせる水準だった。
- **effort を上げる価値があった項目**: low → medium は、コストが tokens で 1.2 倍、時間で 1.2 倍に対して、S11 が ×→○ になった(音量は low と medium のどちらも超過)。medium → high は tokens 1.6 倍、時間 2.0 倍で、音量の遵守と、環境光・喜びポーズなどの演出が増えた。high → xhigh → max は tokens 1.8 倍・1.4 倍、時間 2.3 倍・1.5 倍で、Must / Should の数は変わらず、密度・作り込み・検証ツールが増えた。**「遊べる・仕様どおり動く」だけが目的なら medium で十分**で、それ以上は見た目・演出・音の作り込みに対する投資になる。
- **自己申告と実測のズレ**(自己チェックの正直さ)
  - `low`: README で多くの項目を「未確認」と正直に書いていたが、実測ではほぼすべて合格していた(控えめな申告)。BGM・ジングルの音量超過には触れていない。
  - `medium`: Must の自己申告は実測と一致した。「BGM/SFX のバランスは未調整の可能性がある」と書いていたが、仕様の音量(BGM 0.2 以下)との照合はしておらず、実測で BGM・ジングルの超過を確認した。死亡中の入力の持ち越しには触れていない。
  - `high`: 自己申告は実測と一致。BGM のピークを自己測定で 0.13〜0.17 と書いていたが、実測は 0.176〜0.203(SFX バスを下げたあとの再測定をしていなかった)。
  - `xhigh` `max`: 自己申告と実測がおおむね一致。`max` の BGM ピーク(自己測定 0.192)は、出力捕捉の実測(0.192)と同じ値だった。S13 のカウントアップを作っていないことも README に正直に書いていた。小さなズレとして、`max` は敵 4 種がすべて 4 フレームと書いていたが、ゴーレムの待機は実測 3 だった(検出感度の限界の可能性あり)。
  - 全実装に共通: 音を聴いて確認していない点を README に書いていた。

### 仕様書の問題点

(実装比較中に見つかった、仕様の曖昧さ・矛盾。仕様書は実装開始後に書き換えない。)

- **受け入れ基準が飽和した**: 全員が Must 40/40 で、effort の差をほとんど弁別できなかった。次の仕様書では、Should を増やす、演出の質を段階で採点する基準を入れる、Must の許容を厳しくする、などの工夫が要る。
- **音量の規定が基準の外**: 6.3 節に「効果音 0.35 以下・BGM 0.2 以下」とあるが、受け入れ基準に入っておらず、`low` `medium` の超過を Must / Should の合否に反映できなかった。
- **文字の大文字化の矛盾**: 5.1 節・A18 が「小文字は大文字に変換して描く」と「字形に `x` を含む」の両方を書いた。`x3`(HUD)の表記が `X3` / `x3` に分かれた。
- **ボーナス加算のタイミング**: 3.10 節と 5.5 節が、クリア画面に入る時点と遷移する時点の両方に読める。
- **死亡中の入力**: 入力バッファ(3.4 節)と死亡中の扱い(3.8 節)の相互作用が未規定で、入力の持ち越しに差が出た。
- **観察方法のない基準**: 点滅(M17・M22)、アニメ枚数(S11)は、判定に使う `snapshot()` の項目がなく、画素の測定に頼った。`snapshot()` に「点滅中か」「アニメフレーム番号」を足すと、判定しやすくなる。
- **ゴーストの追跡(M21)**: 仕様の規則が確率的(逆走しない・25% 徘徊)なので、判定が不安定になる。16 か所での接近率をスライムと比べる方法で代用した。
- **良かった点**: `?seed` と `?debug=1` のフック、決定的なステージ生成、`window.__GAME__.snapshot()` の形式の確定により、自動評価が可能になった。

## 評価の方法と限界

- 測定コードは [`eval/`](eval/)。仕様 3.3 の参照アルゴリズム、爆風のシミュレーション、Playwright による操作、音の出力の捕捉を含む。再現手順は [`eval/README.md`](eval/README.md)。
- **未計測・未実施**: ボットが実入力だけで全ステージを遊び切る検証。音を聴いての評価(音色・曲の良し悪し)。歩行 4 フレーム(`medium` 以上の README の自己申告をそのまま採用)。実機のタッチ操作。Chromium 以外のブラウザ。ゲームとしての面白さ。
- 目視で判定した項目: M28, M36, M37, S3, S5, S11, S12, S13, S15(根拠は [`eval/manual.json`](eval/manual.json))。ほかの項目は自動測定の合否。
- 測定中に、評価側の測り方の誤りが何度も見つかり、そのたびに直した(キー入力が短すぎる、点滅の検出が色・位置に依存する、など)。誤りの多くは、最初の測定で実装が不合格に見えた原因になったが、実装側の不具合ではなかった。最終の結果は、直したハーネスで 5 実装を測り直したもの。

#### 主観評価について

上の 5 実装の評価には 1〜5 の主観評価のルーブリックがなく(`EVAL.md` もない)、アセットの違いを文章で比べている。後から尺度を作ると基準の後付けになるため、参考実装にも**点数は付けず**、同じ粒度の文章で書く(根拠は [`eval/screens/opus-medium/`](eval/screens/opus-medium/) と [`eval/screens/fable-high/`](eval/screens/fable-high/) の `sheet-a.png`・`sheet-b.png`・`stage-bomb-flame.png`・`enemy-idle-strips.png`)。

### 所見(参考実装)

#### 実装の違い

- **動作・完成度**: 2 実装とも Must 40/40、コンソールエラー 0 件で、上の 5 実装と同じく、数値・状態遷移・ステージ生成・保存・入力で差は出なかった。差が出たのは、S11(既存の測り方でゴーレムが 1 フレーム)、音量の規定(2 実装とも超過)、細かい相違(`opus-medium` の死亡中の入力の持ち越し、`fable-high` の小さい文字)。
- **ゲームとしての手触り・面白さ**: 移動・導火線・炎・敵の速度は仕様で固定され、実測も上の 5 実装とほぼ同じ(移動 4.51 / 4.50 タイル/秒、ステージ 4 の敵速度は期待値と一致)。面白さは評価していない(未計測)。
- **アセット**: 2 実装ともすべてコードで生成し、画像ファイルは favicon だけ(`opus-medium` は SVG、`fable-high` は PNG)。画づくりの方向は、`opus-medium` が 2px ドット(上の `low` `medium` と同じ粒度)、`fable-high` が 1px ドット(上の `high` 以上と同じ粒度)。
- **仕様の解釈の違い**: ライフ表示は `opus-medium` が `X3`、`fable-high` が `x3`(上の 5 実装でも分かれた点)。ゴーレムのアニメを歩行中だけにした点は 2 実装で共通(仕様 A07 が「2 フレーム(歩行)」と書いているための読み方)。

#### 自己申告と実測のズレ(README の自己チェック・既知の問題の再確認)

- `opus-medium`
  - Must / Should の自己申告は、S11 を除いて実測と一致した。S11 は「golem 4」と申告していて、歩行中の補足測定では 4 だったが、既存の測り方(待機中)では 1。
  - 既知の問題「音は耳で確認していない」: こちらも聴取はしていない(未計測)。出力の捕捉では BGM(title 0.28・stage4 0.62)と gameOver のジングル(0.45)が仕様の音量を超えていた。README は「BGM バス 0.6 x 各声 0.14 以下」と書いているが、実際の出力のピークとの照合はしていなかったと見られる。gameOver / gameClear のジングルが目安より短い(1.9 秒 / 2.7 秒)ことにも触れていない。
  - 既知の問題「`prefers-reduced-motion` の分岐はエミュレーションで未確認」: S2 の測定(Playwright の `reducedMotion: 'reduce'`)で、揺れが止まることを確認した。揺れ自体も、通常時に外壁と床の境界が 3 つの位置に動くことで確認した(README は「スクリーンショットの確認なし」と書いていた)。
  - 既知の問題「2 キーをほぼ同時に押すと、右の 1 歩を終えてから下へ曲がる」: その押し方は**未計測**。M12 の「下を押しっぱなし中に右を追加すると右へ曲がる」は合格。

  - Must / Should の自己申告は、S11 を除いて実測と一致した。S13 のカウントアップを入れていないことは README に正直に書いてあり、実測(`INFO-countup` 1 種)とも一致。

#### 既知の制約

- **物理的な隔離ができていない**: 実装担当の worktree には、`main` にあった既存の 5 実装(`impl/low` など)が最初から含まれていた。エージェント定義で「他の実装を読まない」と禁止しているだけで、見えない状態にはなっていない。そこで、参考実装のコード・アセットが既存 5 実装と酷似していないかを、7 実装すべての組み合わせで同じ方法で調べ、既存 5 実装どうしの値を「同じ仕様書から独立に書いた場合の基準」にした(スクリプトと生データは [`eval/similarity/`](eval/similarity/))。
  - **ファイルのハッシュ**(`impl/<v>/` 以下の全ファイル、完全一致と空白を除いた一致): 7 実装のどの組でも一致なし(favicon を含む)。
  - **コードの類似**(`dist/` の JS / HTML / CSS。一致率は「A の特徴のうち B にもある割合」):

    | 正規化した行(25 文字以上)の一致率 | 0.04%〜1.9%〜4.5% | 6.8%(xhigh) | 7.2%(max) | 5.5% / 5.3% |

    | 識別子を置き換えた 12-gram の一致率 | 4.4%〜9.9%〜16.4% | 16.5%(xhigh) | 17.4%(max) | 13.9% / 14.8% |
    | 16 進カラーコードの一致率 | 2.7%〜5.7%〜11.5% | 10.2%(xhigh) | 6.5%(xhigh) | 2.9% / 3.3% |
    | 最長の共通トークン列(トークン数) | 69〜80〜254 | 194(medium) | 365(max) | 150 |

    参考実装から既存への一致率は、既存どうしの最大値を**少し上回る**(行 6.8〜7.2% 対 4.5%、12-gram 8.2% 対 7.4%)。共通する行の中身を見ると、`snapshot()` の形(`bombs: G.bombs.map(...)` など、仕様 7.4 節の形をそのまま書いたもの)、ステージ表、操作説明の文字列の配列、安全地帯の集合、アイテムの上限処理(`Math.min(6, p.range + 1)`)など、仕様書から同じ形に落ちる行が中心だった。最長の共通列の 365 トークン(`fable-high` と `max`)は、5x7 フォントの字形表(`'J': ['..###', ...]` の同じ書式で、同じ字形が 8 文字ほど続いた部分)で、字形の一致率 82.5% は既存どうしの範囲内。一般的な 5x7 フォントに収束した結果と見られる。`opus-medium` の 194 トークンはステージ表(仕様 3.11 の数値)。どの組でも、関数や処理のまとまりが丸ごと一致する箇所は見つからなかった。
  - **スプライトの画素比較**(`asset-similarity.js`): このゲームには画像の一覧画面がないため、7 実装に同じ操作列(タイトル、ステージ 1〜5 で歩行・爆弾・アイテム・敵 4 種・出口・撃破・クリア、死亡 → gameOver)を流し、画面外の canvas から `drawImage` で描かれた元の矩形(4〜64px 角、単色でないもの)を取り出して、同じ大きさの絵どうしを比べた(比べた絵の数: low 276・medium 986・high 1,474・xhigh 566・max 664・opus-medium 594・fable-high 465)。RGBA の**完全一致は 7 実装のどの組でも 0**。画素距離 8 以下の「ほぼ同一」は、既存どうしで 0〜2.2%、参考実装と既存の間で 0〜0.9%、参考実装どうしで 0.7〜0.9%。「ほぼ同一」になった絵をすべて画像にして見たところ、ステージ 4・5 の暗い無地の床タイル(色と細かいノイズが近いだけ)で、キャラクター・アイテム・柱・岩の一致はなかった。
  - **結論**: 調べた範囲では、参考実装が既存 5 実装を写した形跡(ファイル・関数・絵の一致)は**見つからなかった**。一部の指標が既存どうしの最大をわずかに上回ったが、中身は仕様書由来の定型と一般的なフォントだった。
  - **確認方法の限界**: 読んだうえで書き直した(構造や発想を借りた)場合は、この方法では検出できない。一致率は相手のコード量に左右される(既存の中で大きい `xhigh` `max` が最大の相手になりやすい)。画素比較は `drawImage` を通る絵だけで、`fillRect` で直接描く部分、反転・拡大・色替えした流用は拾えない。favicon はハッシュの比較だけ。音(曲のメロディ)の類似は調べていない。実装担当が既存の実装を読んだかどうか自体は確認できない。
- **評価担当も Opus 5.5**: `opus-medium` は評価担当と同じモデルの出力で、偏りが残る可能性がある。これを抑えるため、合否は上の 5 実装と同じスクリプト・同じしきい値の自動測定を中心にし、目視の項目(`manual.json`)も上の 5 実装の書き方に合わせた。S11 は、同じ基準を当てて 2 実装とも × にした。
- **評価の枠組みが `sunset-rush` と違う**: このゲームは、上の 5 実装をオーケストレーターが `EVAL.md` なしで測り、今回の 2 実装を評価担当が同じスクリプトで測った。`sunset-rush` は評価担当が `EVAL.md` を先に書いてから測っている。測定の枠組みもスクリプトも違うので、**両ゲームの結果を同じ物差しで比べてはいけない**。
- **参考実装は別枠**: 各モデルのデフォルト effort での振る舞いを見るためのもので、モデル間の優劣を断定する材料にしない。
- **実装時の環境**(実装担当の報告に基づく**自己申告**。評価担当が実測したものではない):
  - `opus-medium` の担当は、検証用ポート 5106 が別ゲーム(`sunset-rush/opus-medium`)の担当に使用中だったため、5116(深いサブパスは 5117)で検証した。README には仕様どおり 5106 と書いている。
