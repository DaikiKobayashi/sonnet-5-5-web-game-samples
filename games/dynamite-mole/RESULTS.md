# Dynamite Mole — 実装比較の結果

> 数値は実測したものだけを書いている。測っていないものは「未計測」と書く。
> 評価は、実装担当の自己申告ではなく、評価者(オーケストレーター)がブラウザで測った結果。測定コードと生データは [`eval/`](eval/) にある。

## 評価の方針

「全く同じである必要はなく、遊べる(起動でき、動かせて、クリアまでできる)形であればよい。仕様書にどれくらい従っているかも見たい」という方針で、次の 2 つを分けて見た。

1. **遊べるか**: 起動する・動かせる・爆弾で敵を倒せる・ステージをクリアして先へ進める・ゲームオーバーからやり直せる。
2. **仕様書への従い方**: 受け入れ基準 Must 40 件 / Should 15 件の達成度と、番号のついた基準に入らない相違点。

## 所見

### 実装の違い

- **動作・完成度**: Must は全員 40/40 で、動作の正しさ(数値・状態遷移・ステージ生成・保存・入力)では差が出なかった。差が出たのは、Should の S11(`low` のみ ×)、音量の規定、細かい相違(死亡中の入力の持ち越し、見た目の不具合)。
- **ゲームとしての手触り・面白さ**: 移動速度・導火線・炎の寿命・敵の速度・ステージ表などは仕様で数値が固定されているため、実測でも 5 実装でほぼ同じ(移動 4.48〜4.51 タイル/秒 など)。手触りの差は、数値ではなく、演出・アニメ・音・見た目に出る。面白さは評価していない(未計測)。
- **アセット(画づくり・アニメーション・音)の違い**: すべてコードから生成(PNG は favicon のみ、または全くなし)。差が大きかった項目。
  - `low`: 2px ドットの素朴な絵。敵の待機アニメは 2 フレーム。ゴーレムはほぼ静止。プレイヤーの待機の呼吸なし。
  - `medium`: 2px ドットで、太く読みやすい絵。敵は 3〜6 状態、待機の呼吸あり。環境光は弱い。
  - `high`: 1px ドットの細かい絵。壁の松明・光の漏れ・蛍・専用の喜びポーズ。
  - `xhigh`: 1px ドット。ビネット・壁の松明・ランタンの鎖・火の粉。ゴーストの追跡時の表情変化。
  - `max`: 1px ドット。火の粉・ゆらぐ松明・敵ごとに色分けされた死亡エフェクト・喜びポーズと紙吹雪・タイトルの視差と蛍。
  - 音: 5 実装とも Web Audio で合成し、title + ステージ 1〜5 がすべて別の曲、残り 30 秒以下でテンポが上がる。音量は `xhigh` `max` が仕様の範囲内、`high` がほぼ範囲内、`low` `medium` は BGM・ジングルとも超過(`low` の stage4 は 0.83 でクリップに近い)。
  - 見比べる画像: [`eval/screens/`](eval/screens/) の `sheet-a.png`(タイトル・導入・ステージ 1〜5・エンティティ)、`sheet-b.png`(出口・結果画面・一時停止)、`stage-bomb-flame.png`(5 ステージの床の上の爆弾と炎)、`enemy-idle-strips.png`(敵の待機アニメ)。
- **コード品質(構造・読みやすさ・テスト)**: 量は次のとおり(dist の JS / HTML の行数、バイト数)。行数だけでは品質は測れず、可読性は未評価。

- **仕様の解釈の違い**: 仕様が両方の読み方を許した点で分かれた。ライフ表示の `X3` / `x3`、ステージクリアのボーナス加算のタイミング(クリア画面に入る時点か、次へ遷移する時点か。`low` `xhigh` は入る時点、`medium` は遷移時と README に記載)、死亡演出中の入力の扱い(`low` `medium` は持ち越す)。

### effort による差

- **差が出た点**
  - Should の満点率: low 14/15、medium 以上は 15/15。アニメの枚数(S11)が分かれ目。
  - 音量の規定の遵守: high 以上が範囲内(high はほぼ)、low / medium は超過。
  - 演出・アセットの密度: effort が上がるほど、光・粒子・アニメ・装飾が増える。xhigh と max の差は、Should の達成度ではなく、密度と作り込み(max の敵ごとの死亡エフェクトなど)に出た。
  - 自己検証の量: `xhigh` は 3 ファイル、`max` は 21 ファイルの検証ツールを自分で書いて確かめていた。
- **差が出なかった点**: Must の合否(全員 40/40)、数値の正確さ(移動・導火線・炎・速度・タイマー)、仕様 3.3 のステージ生成(全員、参照実装と完全一致)、コンソールエラー(全員 0 件)。受け入れ基準の多くは、low でも満たせる水準だった。
- **effort を上げる価値があった項目**: low → medium は、コストが tokens で 1.2 倍、時間で 1.2 倍に対して、S11 が ×→○ になった(音量は low と medium のどちらも超過)。medium → high は tokens 1.6 倍、時間 2.0 倍で、音量の遵守と、環境光・喜びポーズなどの演出が増えた。high → xhigh → max は tokens 1.8 倍・1.4 倍、時間 2.3 倍・1.5 倍で、Must / Should の数は変わらず、密度・作り込み・検証ツールが増えた。**「遊べる・仕様どおり動く」だけが目的なら medium で十分**で、それ以上は見た目・演出・音の作り込みに対する投資になる。
- **自己申告と実測のズレ**(自己チェックの正直さ)
  - `low`: README で多くの項目を「未確認」と正直に書いていたが、実測ではほぼすべて合格していた(控えめな申告)。BGM・ジングルの音量超過には触れていない。
  - `medium`: Must の自己申告は実測と一致した。「BGM/SFX のバランスは未調整の可能性がある」と書いていたが、仕様の音量(BGM 0.2 以下)との照合はしておらず、実測で BGM・ジングルの超過を確認した。死亡中の入力の持ち越しには触れていない。
  - `high`: 自己申告は実測と一致。BGM のピークを自己測定で 0.13〜0.17 と書いていたが、実測は 0.176〜0.203(SFX バスを下げたあとの再測定をしていなかった)。
  - `xhigh` `max`: 自己申告と実測がおおむね一致。`max` の BGM ピーク(自己測定 0.192)は、出力捕捉の実測(0.192)と同じ値だった。S13 のカウントアップを作っていないことも README に正直に書いていた。小さなズレとして、`max` は敵 4 種がすべて 4 フレームと書いていたが、ゴーレムの待機は実測 3 だった(検出感度の限界の可能性あり)。
  - 全実装に共通: 音を聴いて確認していない点を README に書いていた。

### 仕様書の問題点

(実装比較中に見つかった、仕様の曖昧さ・矛盾。仕様書は実装開始後に書き換えない。)

- **受け入れ基準が飽和した**: 全員が Must 40/40 で、effort の差をほとんど弁別できなかった。次の仕様書では、Should を増やす、演出の質を段階で採点する基準を入れる、Must の許容を厳しくする、などの工夫が要る。
- **音量の規定が基準の外**: 6.3 節に「効果音 0.35 以下・BGM 0.2 以下」とあるが、受け入れ基準に入っておらず、`low` `medium` の超過を Must / Should の合否に反映できなかった。
- **文字の大文字化の矛盾**: 5.1 節・A18 が「小文字は大文字に変換して描く」と「字形に `x` を含む」の両方を書いた。`x3`(HUD)の表記が `X3` / `x3` に分かれた。
- **ボーナス加算のタイミング**: 3.10 節と 5.5 節が、クリア画面に入る時点と遷移する時点の両方に読める。
- **死亡中の入力**: 入力バッファ(3.4 節)と死亡中の扱い(3.8 節)の相互作用が未規定で、入力の持ち越しに差が出た。
- **観察方法のない基準**: 点滅(M17・M22)、アニメ枚数(S11)は、判定に使う `snapshot()` の項目がなく、画素の測定に頼った。`snapshot()` に「点滅中か」「アニメフレーム番号」を足すと、判定しやすくなる。
- **ゴーストの追跡(M21)**: 仕様の規則が確率的(逆走しない・25% 徘徊)なので、判定が不安定になる。16 か所での接近率をスライムと比べる方法で代用した。
- **良かった点**: `?seed` と `?debug=1` のフック、決定的なステージ生成、`window.__GAME__.snapshot()` の形式の確定により、自動評価が可能になった。

## 評価の方法と限界

- 測定コードは [`eval/`](eval/)。仕様 3.3 の参照アルゴリズム、爆風のシミュレーション、Playwright による操作、音の出力の捕捉を含む。再現手順は [`eval/README.md`](eval/README.md)。
- **未計測・未実施**: ボットが実入力だけで全ステージを遊び切る検証。音を聴いての評価(音色・曲の良し悪し)。歩行 4 フレーム(`medium` 以上の README の自己申告をそのまま採用)。実機のタッチ操作。Chromium 以外のブラウザ。ゲームとしての面白さ。
- 目視で判定した項目: M28, M36, M37, S3, S5, S11, S12, S13, S15(根拠は [`eval/manual.json`](eval/manual.json))。ほかの項目は自動測定の合否。
- 測定中に、評価側の測り方の誤りが何度も見つかり、そのたびに直した(キー入力が短すぎる、点滅の検出が色・位置に依存する、など)。誤りの多くは、最初の測定で実装が不合格に見えた原因になったが、実装側の不具合ではなかった。最終の結果は、直したハーネスで 5 実装を測り直したもの。
