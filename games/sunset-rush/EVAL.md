### 0.2 共通の計測フック(全実装に同じものを `addInitScript` で入れる)

実装のコードには触れず、ページ側に次の観測用フックだけを入れる。フックが原因で実装が壊れた場合は、そのフックを外して再測定し、該当項目を「未計測」とする。

1. **エラー収集**: `console`(type = `error`)、`pageerror`、`requestfailed`、ステータス 400 以上のレスポンス、`localhost:<port>` 以外へのリクエストを Node 側で全件記録する。`console` の `warning` は別枠で件数だけ記録する(合否には使わない)。
2. **フレーム計測**: `window.requestAnimationFrame` を薄くラップし、(a) rAF のタイムスタンプ列、(b) 各 rAF コールバックの実行時間(`performance.now()` の前後差)を記録する。
3. **音の出力タップ**: `AudioNode.prototype.connect` をラップし、`AudioDestinationNode` へ接続しようとしたノードを、コンテキストごとに 1 つ作った `AnalyserNode`(fftSize 2048)経由で destination へつなぐ。これで **実際の出力の RMS・ピーク・周波数分布** を読める(ミュート確認、音が鳴っているかの確認、音割れ=ピーク ≥ 0.99 の検出、スペクトログラム画像の作成に使う)。`AudioContext` の生成回数と `state` も記録する。
4. **テキスト描画の監視**: `CanvasRenderingContext2D.prototype.fillText` / `strokeText` をラップして呼び出し回数を数える(M40)。
5. **30fps 化(M37 のときだけ)**: `requestAnimationFrame` を `setTimeout` ベース(33.3 ms 間隔、コールバックには `performance.now()` を渡す)に差し替える。高 FPS 参考値として 6.94 ms 間隔(144fps)版も 1 回だけ流す(合否には使わない)。

### 0.3 状態の読み方・入力の送り方

- 状態は `window.__game.getState()` を読む。時刻に敏感な測定(タイマー・加速・無敵時間など)は、**ページ内の rAF ループ**で毎フレーム状態をサンプリングして `performance.now()` と一緒に配列に貯め、最後に Node へ返す(Node との往復遅延を除くため)。rAF の実行順により ±1 フレーム(約 0.017 秒)の誤差はあり得るものとして閾値に含める。
- 入力は原則 `page.keyboard.down/up`(trusted なキー入力)。`KeyboardEvent.code` 準拠なので `ArrowUp` / `KeyW` / `Enter` / `Space` / `KeyP` / `Escape` / `KeyR` / `KeyQ` / `KeyM` / `KeyF` を使う。
- 例外: 自動運転ボット(§1.3)と `repeat` テスト(M35)は、ページ内で `window.dispatchEvent(new KeyboardEvent('keydown', {code, key, repeat}))` を送る。実装が合成イベントを無視する場合(対照テスト: 合成 `ArrowUp` を 0.5 秒送って `speedKmh` が上がらない)は、ボットを Node 側 `page.keyboard` + 16 ms ポーリングに切り替え、`RESULTS.md` に記録する。
- **安全ライン SAFE_X = +0.333**: レーン中心 0 / 0.667 と、当たり半径(自車 0.10 + 相手最大 0.13 = 0.23)から、`playerX = 0.333` は仕様どおりの実装なら交通車にも路側 solid にも当たらない。衝突させたくない測定ではこの位置を使う(`setPlayerX(0.333)` を毎フレーム呼ぶか、ボットで保持)。ここで衝突が起きた場合は、それ自体を所見として記録する。
- **スレスレ得点(S-07)を避ける速度**: 追い越し得点の測定は 170 km/h で行う(S-07 は 180 km/h 以上でのみ +20 が入るため、+50 の単独ジャンプを観測できる)。

### 1.2 ロード時間(O-2)

- 新しいコンテキスト(キャッシュなし)で既定 URL を開く。これを 3 回繰り返し中央値を採る。
- (a) `performance.getEntriesByType('navigation')[0].loadEventEnd`(ms)、(b) ナビゲーション開始から `window.__game.getState().scene === 'title'` を最初に観測するまで(ms、ページ内 rAF でポーリング)。
- `RESULTS.md` の「ロード時間」欄には (b) を書き、(a) は results.json に残す。

### 1.3 通しプレイ(O-3)

2 つのルートで測る。どちらも `?seed=42&debug=1`、1 つのページで連続して行う。

**W ルート(warp 補助、標準通しシナリオ)** — M02・M41 の判定に使う。

1. タイトルで `Enter` → `countdown` → `playing` を待つ。
2. ステージ 1: `warp(2950)`、`ArrowUp` を押しっぱなし、SAFE_X を保持 → `stageclear` → パネルが出る 1.7 秒後に `Enter`。
3. ステージ 2: `warp(3550)` で同様(goalZ から約 50 m 手前)。ステージ 3: `warp(4150)` で同様 → `ending`。
4. `ending` で `rank` と `score` を記録し、§3.9 の閾値どおりか照合 → `Enter` で `title`。
5. `Enter` → ステージ 1 `playing` → `setTime(1)` → `timeup` → `gameover` → `R` → `countdown` を確認 → `Escape` 相当の経路確認は M30 で行う。
6. 各遷移で、`stage`・`timeLeft`(countdown 時にステージ開始時間)・`trafficTotal`・`score`(引き継ぎ)・`checkpointsPassed = 0` を記録。

合否: 全遷移に到達し、フリーズ(10 秒以上 scene が変わらない予期しない停止)と状態の混線がなければ「通しプレイ = ○」。

**B ルート(ボット運転、warp なし)** — 参考指標。仕様どおりの物理で実際にクリアできるかと、プレイ時間の実測。

- ページ内の自動運転ボット(全実装で同一コード): 毎フレーム `playing` のとき
  - `err = playerX − 0.333`。`err < −0.02` なら `→`、`err > 0.02` なら `←`、それ以外は操舵なし。
  - `|err| < 0.08` なら `↑`、`0.08 ≤ |err| < 0.15` なら何も押さない、`≥ 0.15` なら `↓`。
  - キーは状態が変わったときだけ keydown / keyup を送る。`stageclear` ではパネル表示後(1.7 秒後)に `Enter`、`ending` で停止、`gameover` で停止。
- 記録: ステージごとのクリア可否、所要時間(`playing` 開始からゴールまで)、ゴール時の `timeLeft`、`crashes`、`overtakes`、最終 `score` と `rank`。
- このボットの結果は Must の合否には直接使わない(ボットの性能に依存するため)。ただし SAFE_X 走行中に衝突が起きた場合は、当たり判定の仕様逸脱の手がかりとして所見に書く。

### 1.4 パフォーマンス(O-4)

- シナリオ P1(主指標): `?seed=42&debug=1&stage=3` を開き、`Enter` → `playing` になってから 2 秒待ち(ウォームアップ)、B ルートのボットで **20 秒間** 走行。最も描画負荷が高いステージ 3(交通車 72 台・ビル)で測る。
- シナリオ P2(参考): タイトル画面で 10 秒。
- §0.2 の 2 のフックから算出:
  - **平均 FPS** = 区間内のフレーム数 ÷ 区間秒数。
  - **最小 FPS** = 区間を 1 秒ごとの窓に区切ったときの、窓内フレーム数の最小値。
  - 参考: 最長フレーム間隔(ms)、フレーム間隔の p99、rAF コールバック実行時間の平均・p95・最大(ms。仕様 §7.5 の「16 ms 以内」の目安)、`longtask`(50 ms 超)件数。
- headless・GPU なし環境の数値なので **実装間の相対比較にのみ使う**。1 回測って、明らかな外乱(平均が他の回と 20% 以上違う)が疑われる場合だけ 3 回測って中央値を採り、その旨を記録する。

### 1.5 モバイル幅・レイアウト(O-5、M03 と共用)

ビューポート 390×844(O-5 の主指標)、および M03 の 1280×720 / 1920×1080 / 375×667 のそれぞれで、タイトル画面と `playing` 画面について:

| 観察 | 判定条件 |
| --- | --- |
| canvas の論理サイズ | `canvas#game` の `width === 640 && height === 360` |
| はみ出し | `getBoundingClientRect()` が `0 ≤ left`、`right ≤ innerWidth`、`0 ≤ top`、`bottom ≤ innerHeight`(各 0.5 px 許容) |
| スクロールバー | `documentElement.scrollWidth ≤ innerWidth` かつ `scrollHeight ≤ innerHeight` |
| アスペクト比 | 表示幅 / 表示高さ = 16/9 ± 1% |
| 最大サイズ(参考) | 表示幅 ≈ `min(vw, vh×16/9)` ± 2 px(§5.1。合否には使わず記録のみ) |
| にじみ防止 | canvas の computed `image-rendering` が `pixelated` |

「モバイル幅の崩れ」欄は 390×844 の結果を書く(全条件を満たせば「なし」、満たさない項目があればその内容)。スクリーンショット `o5-390x844-title.png` / `o5-390x844-play.png` を保存する。

## 2. 受け入れ基準の測定手順(Must 42 件)

### 遷移・運転

**M05 カウントダウン**
- 手順: `title` で `Enter` を押し、直後から `ArrowUp` を押しっぱなしにする。`countdown` 開始から 0.5 / 1.5 / 2.5 秒でスクリーンショット。ページ内で `countdown` の間の `speedKmh` と `timeLeft` を毎フレーム記録。`Space` での開始も別ページで確認。
- 合格: `Enter`(と `Space`)で `countdown` に入る。記録中 `speedKmh` の最大が 0、`timeLeft` がずっと 30。目視で 3 枚にそれぞれ `3` `2` `1` が大きく出ており、`STAGE 1` と `SEASIDE` が見える。

**M06 GO! とタイマー**
- 手順: ページ内で `countdown` 開始時刻と `playing` 開始時刻を記録。`playing` 開始 0.3 秒後と 1.2 秒後にスクリーンショット。`playing` 開始から 5.0 秒後の `timeLeft` を読む(入力なし)。
- 合格: `countdown` の長さが 3.0 ± 0.1 秒。0.3 秒後の画像に `GO!` があり、1.2 秒後の画像には `GO!` がない(目視)。5.0 秒後の `timeLeft` が 25.0 ± 0.3。

**M07 アクセル**
- 手順: countdown 中に `setPlayerX(0.333)` はしない(countdown 入りでリセットされる規則のため)。`playing` を検出したら `setPlayerX(0.333)` → `ArrowUp` を押し、その瞬間をページ内で t0 とし、t0 + 3.0 秒の `speedKmh` を読む。続けて `setSpeedKmh(280)`、`ArrowUp` を 2.0 秒押しっぱなし、`speedKmh` の最大値を記録。どちらも `crashes` が増えたら無効(§0.1 の再試行)。
- 合格: 3.0 秒後が 170〜190。上限確認で最大値 ≤ 300.0(+0.01 の丸め許容)。

**M08 ブレーキ**
- 手順: 在 playing で `setPlayerX(0.333)`、`setSpeedKmh(200)` → 直後に `ArrowDown` を 1.0 秒押し、前後の `speedKmh` を比べる。
- 合格: 減少量が 140〜160。

**M09 惰性**
- 手順: 在 playing で `setPlayerX(0.333)`、`setSpeedKmh(200)` → 何も押さず 2.0 秒後の `speedKmh`。
- 合格: 104〜116。

## 4. 主観評価のルーブリック(各 1〜5)

- 採点は、全実装の標準スクリーンショット一式(下表)を **同じ順番で並べて見比べてから** つける。各点数に、根拠となった画像のファイル名か観察した挙動(測定値)を必ず添える。
- 標準スクリーンショット一式: タイトル 2 枚、カウントダウン 3 枚、GO!、ステージ 1 の 6 地点(M13)、チェックポイント通過、衝突連写、コース外、ステージ 2・3 各 3 地点(M20)、ステージクリアパネル、TIME UP、ゲームオーバー、エンディング、一時停止、HUD、ギャラリー全体、390×844。
- 5 段階の中間(例: 4 と 5 の間)は下の点に丸める。

### 4.1 画づくり(アセットの質・統一感)

| 点 | 定義 |
| --- | --- |
| 1 | 多くのアセットが欠けているか、単色の矩形・図形の仮置きに近い。ステージの色調の違いがほとんどない |
| 2 | Must のアセットはそろうが、形が粗く何の物体か判別しにくいものがある。色がちぐはぐで、ステージ間の違いが弱い |
| 3 | すべて判別でき、ステージごとの色調(夕方・黄昏・夜)がはっきり違う。ただし陰影が平板、または一部のアセットだけ画風が浮いている |
| 4 | 16 ビット風の輪郭と 1〜2 段の陰影がそろい、ステージ内で統一感がある。空・遠景・路側物・車が一つの世界に見える |

根拠は主に数値(M07〜M12 の実測、B ルートのクリア可否・残り時間・衝突数、FPS)と、衝突・コース外の挙動。

## 5. 集計方法

- **客観指標と主観評価は混ぜない。** `RESULTS.md` では別の表にする。
- 受け入れ基準: Must は合格件数 / 42、Should は合格件数 / 18。「未計測」の項目は分母から除かず、件数の横に「(未計測 n)」と書く。「判定保留」も同様に明記する。
- 客観指標: 起動可否、エラー件数、平均 / 最小 FPS、ロード時間、ファイル数、dist サイズ、ソース行数、モバイル幅の崩れ、アセット照合表(ギャラリー / 画面)、B ルートの結果。
- 主観評価: 5 項目それぞれの点数と根拠。5 項目の平均は参考として出してよいが、客観指標と足し合わせない。
- **総合点は出さない。** 理由: 客観指標(基準の合否)と主観評価は単位も意味も違い、重みを決める根拠が仕様書にないため。代わりに、Must 合格数 → Should 合格数 → 主観評価の順で並べた比較を所見に書く。

## 6. 公平性の注意(仕様のあいまいさなど)

1. **点滅周期の解釈**: 「0.5 秒周期」(タイトルの `PRESS ENTER`、`timeLeft ≤ 10` の数字)は、1 周期 0.5 秒(0.25 秒ずつ)とも、0.5 秒ごとに切り替え(1 周期 1 秒)とも読める。0.125 秒間隔で 1.5 秒撮るので、どちらの解釈でも点滅が見えれば合格とする。
2. **スレスレ得点(Should)との干渉**: 追い越し +50 の測定で S-07 の +20 が混ざると Must を誤判定するため、170 km/h(180 未満)で測る。
3. **追い越しと衝突が同じステップで起きた場合の順序**が仕様に明記されていない。M17 の「衝突相手は加算されない」は衝突後の抜き去りで確認し、同じステップの順序の違いでは減点しない。
4. **countdown 中の `setPlayerX`**: countdown 入りで `playerX = 0` にリセットされる規則のため、SAFE_X の指定は `playing` に入ってから行う(実装によって countdown 中の指定が残る・残らないの差を出さない)。
5. **`warp` の後退**: 仕様は後退時のチェックポイントの扱いを定めていないので、`warp` は常に前方へだけ使う。
6. **M12 の初速**: 受け入れ基準は初速を書いていない。「落ち着く」とあるため 200 km/h から測り、0 からの結果は参考として記録する(0 から加速しても 75 km/h 付近で止まるのが仕様どおり)。
7. **タイトルの自動走行のつなぎ方**は実装任せ。タイトルで道路が流れていれば、つなぎ目の見た目は減点しない。
8. **headless の制約**: 音は聴けず、FPS は GPU なしの値。音の主観点は §4.4 の根拠に限り、FPS は相対比較にのみ使う。出力タップや 30fps 化のフックは全実装に同じものを入れる。
9. **合成キーイベント**: ボットと `repeat` テストは合成イベントを使う。実装が `isTrusted` を確認して合成イベントを無視する場合は、§0.3 の代替手順に切り替える(実装の不利にしない)。ただし仕様に反する挙動ではないので減点しない。
10. **debug 表示**: `?debug=1` の FPS 表示(S-16)はスクリーンショットに写り込むが、主観評価では減点も加点もしない。
11. **ギャラリーの native サイズ**: M38 の合否は「存在・フレーム数・描画済み」で判定し、native サイズの不一致は照合表に記録するだけにする(受け入れ基準にサイズ一致の記述がないため)。
12. **目視判定のばらつき**: 目視の項目は、5 実装の同じ条件の画像を横に並べて同じ順で判定し、判定に使った画像名を残す。
13. **seed の再試行**: 想定外の衝突で測定が無効になったときの seed 変更は、どの実装にも同じ順(42 → 7 → 1234)で適用する。
14. **M18 の「無敵中は当たらない」**: `getState()` からは周囲の物体の位置が分からないため、無敵切れ後に同じ帯で衝突が起きたかで「当たれる物があった」ことを裏付ける。裏付けが取れない場合は「確認不十分」と書く。
15. **パフォーマンスの揺れ**: 1 実装だけ外乱が疑われる場合も、再測定は §1.4 の同じ条件で行い、全実装の値を同じ方法(中央値)で揃えて報告する。
